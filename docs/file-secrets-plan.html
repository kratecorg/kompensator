Env-Secrets & File-Materialisierung

Plan für Path B — Zertifikatsverteilung als erste-Klasse-Mechanik in kompensator. Erster Wurf ohne Retention.
Stand: 2026-08-01 · Repo: kompensator · Kontext: TLS-Wildcard *.carimco.de auf den Edge-Nodes customer05/06 · Zwei Features: 1 · Env-Secrets (deklariert) 2 · set-key / set-file + File-Materialisierung
Warum Path B. kompensator-Secrets sind heute env-var-gebunden, ein Cert ist aber eine Datei mit Ziel-Pfad und einem Reload. Statt eines externen Verteil-Prozesses schließen wir die Lücke im System: das Cert wird ein normales Secret im infra-Env, ausgeliefert von kompensator selbst. Generierung bleibt extern (customer02 · letsencrypt · do.de DNS-01).
Entscheidungen aus dem Review (eingearbeitet):
  • Env-Key heißt secrets (nicht nodeSecrets) — es sind Env-Secrets; nodes ist optional, genau wie bei Stacks.
  • Reload bei Cert-Änderung niemals per Container-Restart. Zwei wählbare Strategien: Reload-Kommando (z. B. kill -HUP 1) oder Container-Recreate.
  • Getrennte Verben: secrets set-key und secrets set-file.
  • Rekey deckt Datei-Blobs mit ab (in Scope, nicht später).
  • Materialisierungsziel: Host-Pfad (erster Wurf). Volume später.

Die zwei Lücken für Certs: (a) Scope ist (env, stack), nicht der Node/das File; (b) Auslieferung ist Env-Var, nicht Datei auf einen Pfad. Genau diese zwei Lücken adressieren die Features.

Feature 1 Env-Secrets — Deklaration in env.yml

Neuer Block secrets: in der Env-Definition. Jeder Eintrag hat einen name, ein optionales nodes: (Scalar oder Liste, wie bei Stacks — leer = alle Env-Nodes) und — für den Cert-Fall — einen file:-Block mit dem Materialisierungs-Ziel plus der reload:-Strategie. 

name: infra
stacks:
  - name: edge
    nodes: [customer05, customer06]

# NEU: deklarierte Env-Secrets; nodes optional (wie bei stacks)
secrets:
  - name: wildcard-cert
    nodes: [customer05, customer06]                 # optional; leer = alle Env-Nodes
    file:
      path: /etc/haproxy/certs/carimco.de/server.pem  # Host-Pfad (erster Wurf)
      mode: "0640"                                    # optional; Default 0600
    reload:
      # GENAU EINE Strategie waehlen - niemals impliziter Container-Restart:
      command: [docker, exec, edge-haproxy, kill, -HUP, 1]   # HUP-Reload
      # recreate: edge/haproxy                              # Alternative: Container neu erstellen

Storage der Chiffre

environments/infra/secrets/
  edge.yml.age            # (bisher) Stack-Env-Var-Map    ->  EncryptMap
  files/
    wildcard-cert.age     # (neu)   roher Datei-Blob       ->  Encrypt (raw bytes)
Wenig Neucode: secrets.Encrypt/Decrypt können bereits rohe Bytes. Der Blob-Pfad nutzt sie direkt; die Map-Variante bleibt den Env-Var-Secrets (set-key) vorbehalten.

Recipients & Scope

Recipients eines file-Secrets = Controller-Admin + RecipientsForNodes(nodes) (bzw. alle Env-Nodes, wenn nodes fehlt) — dieselbe Mechanik, die Stacks schon nutzen. Nur der/die adressierten Node(s) können den Blob entschlüsseln.

Feature 2 set-key / set-file + File-Materialisierung

2a · Getrennte Verben

# Einzelner KEY in einer Stack-Env-Var-Map (aendert genau einen Wert, nicht die ganze Map)
kompensator secrets set-key  <env> <stack> <KEY> <VALUE>
kompensator secrets set-key  <env> <stack> <KEY> -          # VALUE aus stdin

# Datei-Secret-Blob (name muss in env.yml -> secrets deklariert sein)
kompensator secrets set-file <env> <name> -                  # Blob aus stdin
kompensator secrets set-file <env> <name> @<pfad>            # Blob aus Datei

# Beispiel (Cert-Rotation, auf dem Issuer/Controller):
kompensator secrets set-file infra wildcard-cert - < server.pem

secrets set (ganze Map ersetzen) bleibt bestehen; set-key ist die additive Einzel-Update-Variante. Deine Skizze secret update preprod URL "…" wird damit zu secrets set-key preprod <stack> URL "…".

2b · Materialisierung im reconcile (Host-Pfad)

Neue Phase vor dem Projekt-Deploy: für jedes file-Secret, dessen Scope diesen Node einschließt:

  1. Blob mit der Node-Identität entschlüsseln, Hash bilden.
  2. Hash mit dem zuletzt materialisierten Hash vergleichen (im Status-Doc gespeichert, je Secret-Name).
  3. Nur bei Änderung: atomar auf den Host-Pfad schreiben (tmp + rename), mode setzen.
  4. Nur bei Änderung: die reload-Aktion ausführen.

Kein Volume-Wegwerf-Container im ersten Wurf: direkter Write auf den Host-Pfad, den haproxy per Bind-Mount liest.

2c · Reload — HUP oder Recreate, nie Restart

Harte Anforderung: Eine Cert-Änderung darf haproxy nicht neu starten. Zwei wählbare Strategien pro Secret:
  • reload.command — beliebiges Kommando auf dem Node, z. B. docker exec <container> kill -HUP 1 (hitless reload).
  • reload.recreate — das benannte Projekt via kompensators normalem Recreate neu erstellen (für Consumer ohne Live-Reload).
Ausgelöst wird der Reload ausschließlich bei tatsächlicher Inhaltsänderung (Hash-Vergleich, 2b) — nicht bei jedem reconcile.
Nuance Container-Name: kompensator generiert Container-/Projektnamen (Naming-Schema). Ein hart kodiertes edge-haproxy im command ist fragil. Optionen: (i) kompensator exportiert den aufgelösten Container-Namen als Platzhalter in den Hook; (ii) Reload über docker compose exec des betroffenen Projekts statt docker exec <name>. → kleiner Punkt für die Umsetzung.

2d · Rekey inkl. Dateien

secrets rekey <env> erweitert: rekeyEnv läuft zusätzlich über secrets/files/*.age, entschlüsselt jeden Blob mit der Admin-Identität und verschlüsselt ihn für die aktuellen Recipients des Secrets (aus env.yml → secrets → nodes) neu. Damit kann ein neu hinzugefügter Node (wie eben customer06 via secrets rekey) auch die Datei-Secrets lesen — konsistent zum bestehenden KV-Verhalten.

5 · Scope — erster Wurf

Drin

  • secrets:-Deklaration in env.yml (nodes optional)
  • Blob-Storage secrets/files/<name>.age
  • secrets set-key + secrets set-file
  • Materialisierung auf Host-Pfad + atomarer Write
  • Reload: command (HUP) oder recreate — nie Restart
  • Reload nur bei Inhaltsänderung (Hash im Status-Doc)
  • Rekey inkl. Datei-Blobs

Bewusst später

  • Retention pro Secret (rollierendes Fenster / keep=N)
  • History-Trim analog Status-Branches (trimStatusHistory)
  • Materialisierung in named Docker-Volume (Wegwerf-Container)
  • Env-weiter KV-Namensraum (falls set-key ohne Stack gewünscht)

Retention bleibt raus: ein abgelaufenes Cert ist nicht sensibel, der Key ist age-verschlüsselt und nur vom Node lesbar — angesammelte Blobs in der Git-History sind Hygiene, kein Sicherheitsloch. Churn ist okay.

6 · Restliche Detailpunkte für die Umsetzung

  1. Container-Referenz im Reload-Command: aufgelösten Namen als Platzhalter injizieren oder compose exec nutzen (siehe 2c).
  2. Erlaubt secrets: auch KV-Einträge (env-scoped) oder bleibt KV bei den Stack-Maps? Erster Wurf: file-Einträge; KV bleibt bei Stacks.
  3. Validierung: set-file lehnt einen name ab, der nicht in env.yml → secrets deklariert ist (kein „verwaistes" Blob).
